# 各模块过滤与校验风险审查

日期：2026-09-29。范围：11 个模块的当前 spec/plan 及相关代码分支。此文聚焦前后规则一致性，不重复产品答复表。

**结论：识别 24 个风险检查项，不等于发现 24 个已复现 Bug。** 每项注明代码静态证据、设计缺口或已有原则需要细化。已修复的要事自身关联只作为回归基线；本次没有再修改运行代码，没有用线上数据验证破坏性场景。

代码静态证据表示可以从当前分支读出风险，不代表已确认某次用户数据受损。其余是开发前必须落实的契约与反例。建议和未确认产品规则仍保持待讨论，记账原文及用户答复表不改。

> 答复更新：Q03/Q04/Q06/Q11/Q12 等已按 [用户确认记录](17-confirmed-requirements.md) 回填。风险项是待实现的技术检查，不把已确认产品决定继续当待审批。

## 共同校验契约（此次补入的工程约束）

1. **模型输出不是合法业务对象。** 先解析结构，再校验字段、引用候选、范围与版本；不得用“让模型不要这样做”的提示词代替代码约束。
2. **区分三种集合：候选、用户已选、可提交。** 当前分页没出现不代表失效；已选失效对象仍须显示及可移除。不能隐藏阻塞保存的值。
3. **区分读取与修改规则。** 有历史快照不代表可修改已删除源；用户看见过候选不代表提交时仍有效。提交前回查权威库，长操作结束时再次检查依赖。
4. **区分模型建议清理与用户选择修改。** AI 未确认建议可去重、排自身、去掉不存在的可选引用，并展示原因/数量；必填内容无法校验则报错。用户已选内容、原文、账目不可静默删改或截断。
5. **规则在服务端成立。** 网页按钮禁用不能替代 API 校验。客户端使用同一规则描述提前反馈；后端错误至少指明字段、原因和相关来源，保留可恢复草稿。
6. **空、失败、未处理、失效不是一回事。** 无结果不等于搜索失败；未知冲突不等于无冲突；未解析不等于已理解；AI判定不等于人工确认。
7. **每次确认绑定具体版本。** 候选批次、输入、引用、计划、证据和约定变更后，旧决策不得悄悄用于新对象；异步 UI 回包绑定发起时的编辑会话。
8. **幂等不等于粗糙去重。** 按实际操作或可靠业务身份去重；两个内容相似的独立记录/交易不能因此被合并。

这些规则补充已确认行为的正确性，不替用户决定答复表中的分类、ASR、退款等产品选择，不启动待讨论的 ACT 开发。

## 风险清单与最小反例

### V01 · ALL · 设计缺口

- **依据：** 各模块写了 JSON/字段校验，但没有统一模型输出契约。
- **失败场景：** 模型返回 null、字符串数组、过长标题、未知枚举或额外状态字段；草稿能填入，保存却失败。
- **必须落实：** 模型返回值先校验对象结构、类型、长度、枚举及引用。标题/摘要/分类等业务内容超限不能无提示截断；无效必填字段显示具体原因。模型不能写 priority、confirmed、active、revision 等人工/服务端字段。关联建议可过滤去重，但必须返回被移除项的原因；用户已确认输入不能静默过滤。
- **最小验收：** 模型返回 null、错类型、超长正文、非法枚举和越权字段：无副作用，错误可定位；合法响应可直接进入相同保存校验。

### V02 · ALL · 设计缺口；刚修复的自身关联问题是实例

- **依据：** 各类选择器、分页、已选项以及保存接口的规则未统一。
- **失败场景：** 已选对象被过滤、翻页或删除后，控件不显示但请求仍携带；用户无法取消，只看到笼统报错。
- **必须落实：** 候选列表、已选列表和提交校验共用类型/空间/状态/自身排除规则；候选缺页不代表对象失效。已有选项即使不在当前页，也须显示摘要或失效占位及移除入口。提交时重新核验，失败保留草稿，按字段及具体 ID 返回原因。
- **最小验收：** 选中后翻页、删对象、切换类型：仍可看见与移除旧选项；合法选择提交成功，无隐藏阻塞项。

### V03 · RET · 原文已有原则，实施验收需补细

- **依据：** RET-04/05；server/retrieval.mjs 的 projectFilter 与回查。
- **失败场景：** 先截前 N 条再过滤可能漏掉唯一有效资料；记忆被 projectFilter 放行，若不再校验 scope 就跨范围载入。
- **必须落实：** 过滤在 dense 和 sparse 两路落实；融合后回查 SQLite 当前范围/状态/版本，按稳定游标补取到数量或耗尽，设预算并说明截断。所有实体种类采用相同项目语义，通用记忆按适用范围单独判定，不以 kind=memory 一概放行。
- **最小验收：** 大量过期/跨项目命中在前，正确资料在后仍能找回；失效记忆即使有向量也不进入答案。

### V04 · RET · 设计缺口

- **依据：** RET-P01 canonical 去重 + RET-04 项目过滤。
- **失败场景：** 两个项目里的相同文件合并成一份正文后，只保留一份 project；另一个项目查不到，或错误共享来源信息。
- **必须落实：** 内容去重与来源成员关系分开：保留每个来源路径、项目和版本；按来源关系过滤，再解析 canonical 正文。删除一个来源不自动删除其他来源可用副本；路径/副本选择仍受 E 盘只读边界约束。
- **最小验收：** 同内容两项目各自命中；归档一个来源后另一个仍可打开，原文件哈希不变。

### V05 · RET MEM · 原文已有原则，实施验收需补细

- **依据：** RET/MEM 的 Qwen 迁移附录、后台索引与版本回查。
- **失败场景：** 新旧模型维度相同而向量混用；索引任务迟到回写旧版本；刚确认记忆尚未索引，冲突查询误判没有记录。
- **必须落实：** 索引命名空间绑定实际模型版本/维度/预处理/分段版本；异步写入前后核验源版本，陈旧任务不能清掉新任务。记忆冲突检查合并尚未索引的有效数据库变更；无法保障覆盖时保留候选并阻止激活，不把部分检索说成检查完成。
- **最小验收：** 编辑/删除发生在 embedding 等待期间；新旧模型切换；新激活记忆尚未索引：无旧事实复活或漏冲突后激活。

### V06 · RES · 设计缺口

- **依据：** RES-08 联网失败降级；RES-02 等待补充。
- **失败场景：** 任何工具错误都触发“用已有知识回答”，可能掩盖用户取消、无权读取、非法输入，或悄悄回答未获准范围。
- **必须落实：** 错误必须分类：搜索不可用、超时、限流等能力错误可降级；取消、访问拒绝、输入非法、源版本冲突不能被当联网失败。只降级缺失证据部分，保留已有证据；生成 API 再失败则报错。缺证据交阶段结果与主动网页接力等待分开。
- **最小验收：** 超时可降级；取消后无新请求；引用失效提示具体来源；生成失败不产出伪成功报告。

### V07 · RES · 原文已有原则，实施验收需补细

- **依据：** RES-04/06 的 evidence 和 questionCoverage。
- **失败场景：** 搜索请求成功就全篇标“已核验”；模型给出未抓取链接或引用错号，报告有来源但结论并无支持。
- **必须落实：** 报告引用仅允许本次真实获得且可定位的证据 ID；全文/摘要/回填/模型知识逐条区分。程序校验引用存在及版本，不能声称由结构校验保证事实正确。混合报告逐结论注明未核验，问题覆盖状态不能由模型任意 ID 增删。
- **最小验收：** 返回虚构来源 ID、仅搜索摘要、部分失败后知识回答：标签和覆盖度准确，未知出处不能显示为已查证。

### V08 · ACT · 待讨论框架的技术风险

- **依据：** ACT-01/02/03/05/07；ACT 当前不默认开发。
- **失败场景：** 模型提出未授权工具或更换文件范围；计划已改/任务取消但旧调用还继续提交结果。
- **必须落实：** 未来确认场景后，工具 allowlist、参数 schema、资源归属、计划版本和运行状态均在服务端派发及提交时核验；幂等键绑定执行实例/步骤及输入。同键不同输入报冲突，取消/暂停边界按共享契约。不得因本条启动 ACT 新功能。
- **最小验收：** 非法工具/错类型对象不派发；相同操作重试不重复产物；取消/计划改版时迟到结果不可复活任务。

### V09 · SUP · 原文已有原则；代码分支可见

- **依据：** SUP-03/04/05；server/work-tasks.mjs 的 evidence 与 confirm。
- **失败场景：** 只验证模型 status=satisfied，没有证明所有必选条件都被逐项审阅；验收期间心跳冲突，或修改证据后仍沿用旧结论。
- **必须落实：** 程序保存本次必选条件快照，模型逐 conditionId 返回判定和证据；缺项/重复/陌生 ID/未识别状态均不能满足。确认绑定条件与证据版本，时长独立计算；旧成果只能按已约定用途作背景，不能冒充本次新交付。
- **最小验收：** 漏一项条件、证据改版、只计时/只报告、验收中正常心跳：完成门槛正确，无无关并发失败。

### V10 · SUP · 设计契约存在潜在冲突

- **依据：** SUP 第5节以 taskId/localDay/scheduleVersion 去重，同时要求同日改时不重建实例。
- **失败场景：** 调一次截止时间就产生第二个日实例；旧提醒迟到，把已改期任务再次催办。
- **必须落实：** 逻辑执行日身份与日程版本分离；同一计划日实例原地改约定并递增版本，明确改期的来源与目标，不单凭 scheduleVersion 新建。调度发送前回查实例、约定版本及状态；旧 job 失效。日期/补记时长校验有限值、范围和重复区间。
- **最小验收：** 同日连续改时间、跨日改期、服务重启后无重复实例；旧约定不催，新约定只出现一次。

### V11 · REC · 待确认产品点叠加校验缺口

- **依据：** REC-09/P06；答复表 Q03/Q04 尚待用户填写。
- **失败场景：** AI 填了不存在的分类，或类别改名/移除后旧记录保存失败；强制分类使历史记录、图片导入突然无法保存。
- **必须落实：** 固定类别/项目类别使用稳定 ID；AI 在已存在集合中自动选一个类别，用户可调整并立即登记问题；创建类别仍是明确用户动作。失败保留待分类原文，迟到AI不能覆盖人工修改；旧记录允许兼容状态，移除类别必须处理已有引用。
- **最小验收：** 九类初始化重跑不重复；同名项目校验；旧记录缺分类仍可打开且不丢内容；改类不改变 threadId。

### V12 · REC EVT · 代码静态可见的漏读分支

- **依据：** server/index.mjs 的 notes/:id/summarize 仅在 note.type=image 时取首张；Events 辅助编辑读取图片数组。
- **失败场景：** 文字记录贴图后归纳没读图片；多图只读首张，却让用户以为 AI 已分析全部附件。
- **必须落实：** 决定输入能力时检查实际附件及内容，不只按 note.type。请求记录实际读取的附件 ID/版本/数量，支持范围内的选定图片都纳入；超限或不支持时点名缺失部分并提供拆分，不能默默漏读。OCR/ASR 完成状态与上传状态分开。
- **最小验收：** 文字+图、多图、纯图和不支持附件：实际模型输入与界面声称读取的范围完全一致。

### V13 · REC EVT · 原文已有保护原则，链路需补细

- **依据：** REC 原文/成果版本；EVT 独立图片快照；多处异步文件写入。
- **失败场景：** AI 生成期间来源换了、图删了，迟到草稿覆盖新编辑；剪切或复制失败留下丢图/孤立文件。
- **必须落实：** 异步草稿绑定来源类型/ID/正文及附件版本和请求序号，返回时检查编辑会话仍匹配；不覆盖后来用户输入。独立图片先完整复制校验，再提交关联，失败清理临时副本但不删除原件；附件访问校验对象归属。
- **最小验收：** 辅助编辑期间更换来源或手改正文不被覆盖；第二张复制失败时旧图和记录不丢；下载对应当前保存版本。

### V14 · CHAT REC EVT · 新增需求与现有限制未衔接

- **依据：** CHAT-08 固定自动引用；server/index.mjs resolveConversationReferences 限5条且禁止重复。
- **失败场景：** 会话已有5条引用时，入口再自动追加第6条导致无法发消息；旧来源再次进入时追加成重复引用。
- **必须落实：** 同一 kind+id 自动引用应更新当前引用版本，不追加重复项。为保留五条上限，新增来源将超限时打开可见选择面板并指出必需来源，让用户替换可选项；不静默丢其他引用或另开会话。会话历史引用与当前待发送引用分开。
- **最小验收：** 已有5条时重进同来源仍5条；进入新来源时能看清并解决超限；原threadId和历史不变。

### V15 · CHAT · 设计缺口

- **依据：** CHAT-P02/05 历史摘要、来源映射与自动引用。
- **失败场景：** 在 A 发消息后切到 B，A 的迟到结果进入 B；当前来源更新了，旧摘要仍把旧内容当最新事实。
- **必须落实：** 发送时固定 threadId、请求幂等键及来源版本，不从回调时活动页面重取目标。摘要携带覆盖签名及引用版本，重建采用版本比较，当前引用和历史快照明确分开；选项变动不改写已发送消息。
- **最小验收：** A请求中切B，回包只落A；来源改版后旧事实有历史标识；摘要乱序返回不回退覆盖范围。

### V16 · EVT · 代码静态可见

- **依据：** server/index.mjs eventData 的 reset 只比较 dueAt/summary/priority；server/events.mjs 以 reviewedDueAt 判断重复。
- **失败场景：** 换来源、改标题/图片/关联任务后旧“已复核”仍有效；生成期间来源变了但要事revision没变，旧建议可能看似适用。
- **必须落实：** 复核有效性绑定实际输入依赖签名：要事相关字段、源记录/附件、实际读取的任务/证据版本及约定时间。提交与确认都回查依赖，旧建议保留历史但标过期，不阻碍不需复核的普通提醒；当前要事更新时间一个字段不够。
- **最小验收：** 同时间下更换来源/图片/关联证据后旧建议不作为当前复核；模型等待期间源变更能检出。

### V17 · EVT · 自身关联已修；相邻边界仍需规定

- **依据：** EVT-02/05/08；eventData 与编辑候选生成。
- **失败场景：** 关联要事删除后仍藏在选择状态；AI生成草稿阶段没有当前实体身份；已确认要事编辑状态含混导致误复活提醒。
- **必须落实：** 编辑请求始终带当前 eventId，候选先排自身，建议去重/限10/回查存活，保存仍校验。已有失效关联可见可移除，不静默删用户选择。约定日期合法性服务端负责；Q06 已确认无提醒经历可不设时间，检查确认与要事结束分离；四种类型前后端校验一致，不自动重开已结束要事。
- **最小验收：** 自关联、已删除/重复/超10项、编辑时换来源均有确定结果；直接API与网页规则一致；失效选择可操作。

### V18 · MEM · 代码静态可见

- **依据：** server/engine.mjs findMemoryConflict 返回 find(...parsed.conflictId)||null。
- **失败场景：** 模型返回 {}、未知冲突ID或错误字段类型时，被解释为“没有冲突”，可能放行激活。
- **必须落实：** 冲突结果必须通过完整 schema：无冲突必须显式合法 null；有冲突必须命中本次有效候选、对应主体/范围/时间且带依据。陌生ID/缺字段是检查失败，不是无冲突；保留候选并允许重试，不激活、不删旧记忆。
- **最小验收：** {}、未知ID、数字、空字符串与显式null分别断言；只有格式合法且覆盖完成的无冲突结果才可继续人工确认。

### V19 · MEM · 原文已有原则，需消除 plan 中二选一措辞

- **依据：** MEM-P01/02/03；批次确认、手动编辑/恢复及索引滞后。
- **失败场景：** 同批候选互相冲突却都激活；编辑误把自己当冲突；先删旧记忆，后保存新记忆失败。
- **必须落实：** 所有入口共用检查；编辑排除自己的旧版本而非所有同主题条目，比较当前批次与适用范围有交集的active记忆及未索引变更。确认事务重新校验批次/选项/替换对象/版本，整体提交或整体失败；不凭客户端conflictId直接删对象。检查不完整时不激活。
- **最小验收：** 手动/PATCH/恢复均不可绕过；同批矛盾、并发替换、提交中失败无双active或旧记忆丢失。

### V20 · SET · 设计缺口

- **依据：** SET-01/02/05 配置检测与完整恢复。
- **失败场景：** 改模型后旧测试回包还显示成功；新配置部分保存失败；备份结构可读但引用/附件缺失仍覆盖上线。
- **必须落实：** 配置按能力校验并原子保存；探测结果绑定配置版本，迟到结果不覆盖新配置状态。备份校验schema、实体类型/ID唯一、引用版本、文件清单与哈希、合法相对路径，先隔离恢复；索引版本不能替代权威数据完整性。
- **最小验收：** 测试A期间改B，A结果标过期；一字段非法不部分保存；损坏或缺附件备份不替换当前库。

### V21 · PET · 原文已有原则，需补接口级用例

- **依据：** PET-P01/02/04 的统一聚合、标识与状态更新。
- **失败场景：** 表格过滤稍后项而红点仍计数；处理后旧轮询把提醒复活；跳转链接指向已删对象。
- **必须落实：** 标识、列表、总数从同一有效性谓词/一致快照派生；分页含总数和快照版本。稍后/过期/已处理的归属明确；旧响应不能覆盖新处理状态，入口按来源类型解析。仅关闭/摸摸/汇报不调用确认接口。
- **最小验收：** 处理请求与旧轮询乱序、全部稍后、分页多条、来源删除：表与标识一致，无旧提示复活。

### V22 · FIN · 代码静态可见

- **依据：** server/accounting.mjs parseWechatWorkbook 的 continue 分支及 dateFromExcel。
- **失败场景：** 日期是文本而非Excel序号时跳过；金额/状态不能解析也直接略过；用户看到导入成功却不知道漏了账。
- **必须落实：** 逐非空原始行保留行号及识别/待核对/明确排除/重复状态、原因；汇总数量可与原表核对。支持约定的文本日期和Excel日期格式，非法不能被日期自动进位。存在未处理行时不能称全表完成；错误行不参与统计。
- **最小验收：** 序号日期、文本日期、无效金额和未知状态混合样本：每行可查去向；无静默丢账或错误日期入库。

### V23 · FIN · 代码静态可见；业务选择部分待Q11/Q12

- **依据：** accounting.mjs 缺交易号时使用 date+direction+amount+note 去重。
- **失败场景：** 同天两笔同金额同商户被误删；截图/Excel跨来源重复又未识别；退款和还款重复计算。
- **必须落实：** 来源渠道与交易ID作为重复依据，按Q12提交用户核对；无强ID同样不能按粗略相似键丢行。同次提交重试只做操作幂等，不等于独立导入自动去重。预览确认绑定导入批次/行ID及修订，提交再查重。Q11 已确认退款流水不计、转账计入、花呗按还款记录；Q12 已确认重复项等待人工核对、保留原件；程序统计仅包含已确认有效条目。
- **最小验收：** 两笔合法同额交易不丢；同一确切交易重复提交幂等；预览后库变化仍提示冲突而非重复记账。

### V24 · FIN · 原文校验规则已有，AI到提交映射待补

- **依据：** 用户记账文档类型/分类/金额规则；accounting.mjs validateTransaction/suggestCategories。
- **失败场景：** OCR/AI给出分类别名或错类型类别，前端看似填写但保存拒绝；默认“其他”把识别失败伪装成确认；金额两种字段互相矛盾。
- **必须落实：** 收入/支出分别用明确固定集合，显示文案与存储值映射一致（例如“其他支出”的解释不是新增类别）；金额按一种规范表示，多个金额字段冲突则拒绝，不靠优先级静默选。AI未知项保持待核对，不能自动视为用户确认；统计从服务端确认数据计算。
- **最小验收：** 错类别/跨类型类别、浮点边界、金额字段冲突、识别失败：可修正且无自动入账；确认后的统计与列表一致。
