当前迭代顺序：先完成“记录后 AI 整理建议 + 可见要事”的记录闭环，再把搭子的长期上下文和记忆召回接到这一闭环；高等级主动复核依赖要事结构，放在其后。记账维持入口占位，不进入本轮开发。

## 本轮补充确认

1. 高等级要事在用户约定的日期时间检查，并可以显示在主页面待办事项中；只有高等级要事需要 Agent 提建议。所有要事提醒都必须由用户确认，不能因 Agent 建议而自动完成或自动延期。
2. 测试阶段，每轮对话结束后生成数条提炼过的长期记忆候选。用户手动选择后才更新长期记忆；未选择的候选丢弃。加入时如与既有记忆冲突，立刻让用户确认保留哪一条。
3. 搭子的陪伴风格和主动交互本轮暂不迭代。
4. 第一轮验收场景是上传录音、文字或图片后，用户能够看到相应内容的总结归纳。总结须有真实可核对的提取依据；无法解析时明确提示，不能把文件名或猜测伪装成文件内容。

### 本轮实现与边界

- 文字和图片已接入“上传 → 模型归纳 → 用户可见摘要”流程；用户可在记录详情重新归纳，失败保留原件并明确提示。用真实 `deepseek-flash` 调用验证了普通文字和图片；极小的 1×1 PNG 被模型拒绝，界面会说明需换用普通图片。AI 摘要始终标注需核对原件。
- 对话每轮从用户本轮陈述提炼 0–3 条候选；没有明确稳定事实时返回零条，不编造“几条”凑数。确认所选后其余候选清除；发现与生效记忆冲突时要求保留已有或本轮新记忆。模型未配置或冲突检查失败时不把新事实静默写入长期记忆。
- 要事可由记录转入，也可独立新建；包括标题、摘要、标签、项目、关联要事、等级和约定时间。AI 可填编辑草稿，用户保存后才生效。服务运行时每分钟扫描到期高等级要事并给建议；普通要事不生成建议；所有到点提醒均由用户手动确认，首页显示待确认项。当前是**应用内提醒**，没有系统推送或关机后提醒保障。
- 录音原件仍可保存和回放，但当前没有音频转写服务；在取得语音识别方案前，不宣称录音可自动总结。搭子的陪伴风格本轮未改。

## 产品判断

PersonalAgent 的核心价值暂归纳为两件事：

1. 随时记录，尽量减少用户之后编辑、分类和整理的负担。
2. 成为能理解个人资料、记住上下文并协助推进事情的搭子。

要形成完整体验，需要贯通“收集 → 整理 → 形成可回看的记忆 → 检索/对话/产出”。目前实现和文档愿景之间仍有差距，先通过讨论确认产品边界和优先级，再决定具体实现。

## 讨论顺序

按依赖关系逐项推进：先确认产品主线，再讨论记录整理；随后确定记忆模型和搭子能力，再梳理导航；最后确认同步、地址恢复和实时预览的验收标准。讨论中发现更紧急的阻塞项时，可以调整顺序。

每个议题记录以下内容：

- 用户确认的目标与使用场景
- 已选择的方案及明确不做的范围
- 仍未确定的问题
- 后续文档或实现动作

## 决策记录

第 1 项已确认：两者并重，以“记录—整理—搭子协助”的完整场景作为产品主线。具体首个场景和验收方式仍待后续议题明确。

第 2 项已确认：记录时不强制选择分类、项目或标签；记录保存后由 Agent 生成标题/摘要，并建议标签、项目和相关事件；用户可以确认或忽略建议，原始记录保留。

第 3 项暂定：情节记忆表示有时间和来源的具体事件；长期记忆表示跨任务仍有用的个人偏好、角色和项目背景。用户进一步明确，情节记忆要以用户可见、可编辑的“要事”记录呈现，而不能只供 Agent 内部使用。普通记录可被用户选择转为要事；进入要事编辑后，呈现标题、摘要、标签、项目和相关事件建议。编辑方式可由用户选择直接编辑或交由 Agent 辅助整理；辅助编辑完成后须由用户确认。要事分两个等级：高等级要求 Agent 主动检查事项记录和计划，发现问题时及时提出建议并讨论确认；用户也可选择稍后确认，并指定日期和时间。低等级只保存并可查看、提问，不主动检查或提醒。长期记忆候选确认规则暂定，试用后复核。

第 4 项已明确的方向：搭子主要服务生活化内容、随笔、项目灵感、轻量讨论和头脑风暴，不把深入项目管理当作当前能力承诺。对话需要像常见聊天产品一样按话题分会话；各会话可以跨天继续，不将不同话题的聊天历史混在一起，同时可按需关联该话题对应的记录和长期背景。要事的高低等级由用户确定；高等级主动复核规则按第 3 项执行。

第 4 项会话要求已确认：一个话题一个会话；会话跨天保留并能够接着聊；拆分会话是为了聚焦话题，不代表丢弃同一会话的上下文。以下上下文/记忆方案为待确认设计稿。

第 9 项已确认：成果需要区分“AI 撰写”“AI 辅助整理原文”和“原文整理”；AI 调用失败时前端应说明原因，并提供重试或改用本地原文整理的选择。

第 5 项已确认：主导航采用“记录 / 搭子 / 要事 / 成果”；“我的记忆”作为搭子下的记忆/偏好管理入口，用户可继续查看和管理长期记忆。

第 6 项已确认：手机端分别显示“本机已保存、等待同步”“服务器已保存、电脑待同步”“电脑已同步”；同步失败时显示原因并允许重试。健康检查只表示服务可访问，不能代替数据写入确认。

记忆检索数据库已确认先选用 Qdrant，仍需用本项目中文记录验证检索效果与运行成本；这一选择不代表已经实现记忆检索流程。SQLite 与 Qdrant 的具体数据同步机制仍按下文方案讨论。

第 10 项已确认：记账先保留入口，但暂不开发记账功能。当前占位入口放在电脑端侧栏次级区域和手机端设置页，不加入已确认的四个主导航项；账目数据结构、统计和 AI 辅助方式留待后续讨论。

## 实现核对：当前“我的记忆”

- 当前实现称作 Agent 容易让人误解：核心是关键词检索、固定提示词和单次模型 API 调用组成的流程，没有多轮规划、工具选择/调用、按话题编排记忆或持续任务状态管理。当前属于 Agent 产品方向的早期原型，而不是具备完整 Agent 编排能力的实现。
- 当前上下文也不是会话记忆：模型 API 每次只收到一条 system 和一条 user 消息；问答只带入当前问题及关键词检索出的记录片段，不附带之前的对话。问答历史会保存并显示，但只用于历史列表。成果生成只使用本次模板、项目、时间范围、写作要求、所选记录及范围匹配的长期记忆，不读取先前对话或成果。
- 当前“我的记忆”不是 Skills 或任务工作流管理器，而是简单的长期记忆条目管理：手动添加候选、确认生效、编辑、暂停或删除。
- 当前条目没有“记忆类型”字段；“通用 / 周报 / 文章”是成果生成时的适用范围。
- Agent 的资料问答 `answer()` 不读取记忆条目；当前对话回答不会自动带入“我的记忆”。
- 成果生成 `generateArtifact()` 会自动筛选已生效且范围匹配的条目：通用记忆用于周报和文章，周报/文章范围只用于对应成果。候选、暂停、拒绝或失效条目不参与。
- 这不是按语义判断“此刻需要什么记忆”的智能检索，而是按状态和固定范围筛选后放入生成提示。当前没有从普通对话自动抽取长期记忆的流程。
- 产品信息架构建议仍待讨论：情节记忆应以用户可见的“要事”呈现；长期记忆继续可查看和管理，可考虑放在“搭子”的记忆/偏好管理入口，不应与 Skills 混为一类，也不必占主导航一级入口。
- 成果生成存在多种路径：模型未配置时会回退到本地原文整理且不显示醒目的失败提示；模型异常会把任务标记失败；输出未通过引用校验时会回退到本地整理，并在成果详情显示质量提示。另一个误标风险是，本地模型的成果路径只让模型挑选原文片段，程序拼接原文；如果通过基础格式/引用校验，仍被记为 `mode=model` 并显示“AI 整理”。这可能解释“AI 草稿”与实际内容不符。用户要求 AI 未成功时前端应明确报错/告知。
- 当前服务端默认把 SQLite 数据库放在工作目录下的 `.data/shiguang.sqlite`，可由 `DATA_DIR` 改路径；上传原件单独存于同一数据目录的 `uploads/`。记录正文及元数据以 JSON 存在 `entities` 表的 `data` 字段，另有 kind、revision 等列。`save()` 与变更游标写入在同一 SQLite 事务中；事务提交后接口才返回记录 ID 和 revision。电脑端从同一服务读取数据并轮询 changes 游标。`/api/health` 目前只返回进程健康状态，不执行数据库写入/读取探测。

## 上下文与记忆状态：简单设计提案

### 会话上下文

- 一个会话代表一个话题，跨天继续时沿用同一个会话 ID；新话题由用户新开会话。
- 每轮上下文由固定规则、该会话摘要、最近若干轮对话、与当前话题相关的已确认记忆/要事/原始记录，以及用户本轮输入组成。
- 其他会话的聊天原文默认不带入，避免话题串线；可以检索共享的长期记忆和原始记录，但只取与当前话题相关的少量内容并标注来源。
- 会话变长后，把较早对话压缩成会话摘要，保留最近对话原文；达到长度上限后再压缩。摘要可查看、可重建，不能覆盖原始消息。
- 每轮记录实际使用了哪些记忆和资料，以便查看回答依据。本轮临时要求不会自动变成长期记忆。

### 记忆类型与状态

| 类型 | 用途 | 建议状态/规则 |
|---|---|---|
| 原始记录 | 用户录入的文字、文件、音频等，作为依据 | 原件与版本保留；可检索，不能被摘要覆盖 |
| 情节记忆/要事 | 某件具体发生的事，由用户端专门查看和编辑 | 用户从普通记录转入或确认 Agent 整理；等级由用户设置。低等级只在相关时提供；高等级触发主动复核/预约确认 |
| 长期记忆 | 跨会话仍有用的偏好、个人背景、项目背景 | candidate → active → paused / superseded / expired / rejected / deleted；候选需用户确认后才进入上下文 |
| 会话上下文 | 同一话题下跨天对话形成的连续性 | 仅对所属会话有效；通过近期消息和摘要延续，不自动变成长期记忆 |
| 本轮任务上下文 | 本次问题的临时要求、检索结果和计划 | 只在当前请求使用；完成后不自动保留为个人事实 |

### 每轮检索的简化顺序

1. 用会话 ID 读取该会话摘要和最近消息。
2. 从本轮输入提取话题关键词及项目/时间范围。
3. 为当前话题生成 embedding，在已建立索引的记录片段、要事和已确认长期记忆中做语义检索；再结合关键词、项目、标签、时间和状态过滤，不把整个资料库塞进提示词。
4. 按固定长度预算组装上下文；当前输入和近期对话优先，记忆/记录附来源，冲突信息保留时间与出处。
5. 排除候选、暂停记忆和不相关会话。候选只在用户确认后转为 active。

已确认的检索原则：要做语义召回就必须使用 embedding；关键词匹配只能作为精确词项补充，以及项目、标签、时间、状态等元数据筛选，不能代替语义理解。向量检索数据库先选 Qdrant；下述方案由 SQLite 保存权威的记忆状态与来源关系，Qdrant 保存用于召回的 embedding 和索引数据。每个向量需记录来源 ID、内容版本、片段位置和 embedding 模型版本；记录编辑或删除时重建/移除对应向量。候选及暂停记忆不进入有效记忆召回。每轮保留多少消息、摘要触发时机和主动复核时机仍待细化。

### SQL 与向量库分工：建议方案（待确认）

- SQLite 继续作为权威数据源，保存原始记录、会话、消息、要事、长期记忆及其状态/版本/来源关系；暂停、确认、删除和冲突更新由 SQL 事务管理。
- 向量数据库承担日常记忆检索，保存记录片段、要事和已确认长期记忆的 embedding、可检索文本及 payload（实体 ID、类型、状态、项目、版本、片段位置）。SQLite 保留同一记忆的权威正文、确认状态、来源关系和变更历史；向量库中的文本是检索副本，不作为唯一副本。
- 采用 embedding + 关键词混合检索：dense 向量负责语义召回，sparse/词项索引负责专有名词和原词匹配，再按项目、话题、时间、记忆状态过滤并融合排序。先以 Qdrant 的 dense/sparse 混合查询和 RRF 实施验证；中文词项检索效果需用真实样本检验，必要时配合 SQLite FTS5。
- 为避免两库状态不一致，SQL 写入实体时同事务写入待索引 outbox；后台任务生成 embedding 并 upsert/delete 向量。查询结果再回 SQL 校验实体仍存在、版本一致且记忆状态允许使用。索引可从 SQL 原始数据重建。
- 当前方案：SQLite + Qdrant 独立向量检索服务，两者先部署在同一台电脑。Qdrant 负责相似度/词项召回，SQLite 处理权威数据的保存和状态核对；具体部署与同步方式仍待实施验证。

选型依据（2026-09-24，已确认先用 Qdrant）：Chroma 有 TypeScript 客户端并可自托管，基础向量查询支持字段/文档过滤；但官方源码的 `Collection.search()` 注释写明混合检索接口暂仅适用于 distributed/hosted Chroma，单节点 `SegmentAPI._search()` 明确抛出 NotImplementedError。Qdrant 官方自托管查询文档展示了 TypeScript 的 dense/sparse 双路召回和 RRF 融合，因此在“本机自托管 + 混合检索”这一组合下先用 Qdrant。最终仍要在锁定版本上用相同中文资料测试准确率、延迟、资源占用和重建；不能仅凭接口能力推断中文检索质量。

### 检索术语与本项目示例

- Dense 语义检索：用 embedding 模型把“我上次和朋友闹别扭后想通了什么？”和“与小林发生分歧，后来意识到……”映射成可比较的稠密向量，找出措辞不同但含义相近的记录。
- Sparse 词项检索：记录具体词语的权重，擅长找“小林”“项目代号 A17”这类需要保留原词的内容。它属于词项信号，不等同于记忆状态字段的过滤；中文效果取决于分词/稀疏模型。
- 融合排序：分别取得语义结果和词项结果，再用 RRF 等算法按两份名次合并；同时符合含义和专有词的记录通常更靠前。
- 字段过滤：在检索时限制 `status=active`、所属项目、类型或时间范围。返回候选后仍向 SQLite 核对状态与版本，防止索引更新延迟时误用暂停或旧版记忆。
