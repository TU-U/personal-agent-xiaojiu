# 记账功能 Specification

## 1. 功能目标

实现一个基础记账模块，使用户能够：

1. 手动新增一笔账单
2. 记录收入或支出
3. 设置金额、分类、日期、备注
4. 查看历史账单
5. 修改和删除账单
6. 查看基于账单数据计算出的收支统计

本功能负责**账单记录与统计**，每个月有两次提醒查看账单的时间，第一次是1号，用户手动在微信/支付宝导出excel账单，然后交给记账功能统计；第二次是15号，作用是看看这半个月消费如何。不涉及自动导入支付宝/微信账单。
AI 需要能够分析excel，自动把每一笔消费分类，然后交给用户确认分类，在确认分类之后，AI不做计算工作，计算工作交给写好的程序去统计。
要求统计结果有扇形图，还有每月的条形统计图，每月的消费排名（从高到低），消费排名要显示两种，一个是单笔消费从高到低排名，一个是消费类型从高到低排名。
分类按照以下消费类型：美食、日用、花呗、交通、房租/还款、其他支出（一般是游戏/礼物）、医疗、演出/漫展、旅游、衣物/化妆品、护肤品。不要额外增加分类。
记账功能的主页需要显示这个月目前的收入和支出分别是多少。
以及目前每个月的生活费是2000，需要显示当前还剩下多少生活费。生活费包括：美食、日用、花呗。其他的类型不在生活费范围内。
并且也可能随手记账一笔，可能需要分析账单截图，所以需要支持OCR

## 3. 数据模型

每一笔账单至少包含：

```text
Transaction
├── id
├── type          // income | expense
├── amount        // 金额
├── category      // 分类
├── date          // 发生日期
├── note          // 备注，可为空
├── createdAt
└── updatedAt
```

### 金额规则

* 金额必须大于 0
* 金额最多保留两位小数
* 金额在数据层统一使用一种表示方式
* 不允许使用浮点数直接进行金额累计计算
* 前端展示时统一显示两位小数

### type

只允许：

```text
income
expense
```

### 默认分类

支出：

```text
美食
日用、
花呗、
交通、
房租/还款、
其他支出（一般是游戏/礼物）
医疗、
演出/漫展、
旅游、
衣物/化妆品、
护肤品
```

收入：

```text
工资
奖金
兼职
投资
其他
```

分类设计应允许后续扩展，但本次不需要实现自定义分类。

---

## 4. 新增账单

用户点击“新增账单”后，可以填写：

* 收入/支出
* 金额
* 分类
* 日期
* 备注

默认值：

* 类型：支出
* 日期：当天
* 分类：根据当前类型选择第一个可用分类
* 备注：空

如果是OCR/excel分析，也需要按以上结构

### 校验

提交时：

* 金额不能为空
* 金额必须 > 0
* 金额必须是合法数字
* 金额最多两位小数
* 类型必须合法
* 分类不能为空
* 日期必须是合法日期

校验失败时：

1. 不提交数据
2. 在对应字段附近显示错误信息
3. 不清空用户已经填写的内容

提交成功后：

1. 保存账单
2. 更新账单列表
3. 更新统计数据
4. 关闭新增表单
5. 给用户明确的成功反馈

---

## 5. 账单列表

列表展示：

* 日期
* 类型
* 分类
* 金额
* 备注

支出和收入需要能够被用户直观区分。

列表按照：

```text
日期倒序
```

排列。

同一天内按照创建时间倒序排列。

空数据时显示明确的空状态，而不是空白页面。

---

## 6. 编辑账单

用户可以修改：

* 类型
* 金额
* 分类
* 日期
* 备注

编辑时复用新增账单的校验规则。

修改成功后：

* 更新列表
* 更新统计
* 保留原始 `id`
* 更新 `updatedAt`

---

## 7. 删除账单

用户可以删除账单。

删除前必须进行确认。

删除成功后：

* 从列表移除
* 更新收入统计
* 更新支出统计
* 更新余额

如果删除失败，不应从 UI 中错误地移除该记录。

---

## 8. 统计

至少提供：

```text
总收入
总支出
余额
```

计算规则：

```text
总收入 = 所有 income 类型账单金额之和

总支出 = 所有 expense 类型账单金额之和

余额 = 总收入 - 总支出
```

统计结果必须基于当前有效账单数据实时计算。

筛选条件发生变化时，统计数据也应同步变化。

---

## 9. 筛选

至少支持：

### 日期

* 全部
* 今天
* 本周
* 本月
* 自定义日期范围

### 类型

* 全部
* 收入
* 支出

### 分类

* 全部
* 指定分类

多个筛选条件同时存在时使用 AND 关系。

例如：

```text
本月 + 支出 + 餐饮
```

表示查询：

> 本月所有餐饮支出。

---

## 10. 数据一致性

以下操作完成后必须同步更新相关 UI：

* 新增账单
* 修改账单
* 删除账单
* 修改筛选条件

不得出现：

> 列表已经更新，但统计数据仍然是旧数据。

数据计算应尽量基于统一的数据源，而不是维护多个容易产生不一致的副本。

---

## 11. 错误处理

需要处理：

* 表单校验失败
* 数据保存失败
* 数据读取失败
* 数据删除失败
* 非法数据
* 空数据

错误信息应该让用户知道：

1. 发生了什么
2. 哪一步失败
3. 用户是否可以重试

禁止静默吞掉错误。

---

## 12. 非功能要求

* 保持现有项目 UI 风格

* 优先复用已有组件

### 代码

* 优先复用现有工具、组件和数据层
* 不重复实现已有能力
* 不进行与本功能无关的大规模重构
* 不修改无关模块

## 13. 验收标准

以下场景全部通过后，功能才算完成：

### Case 1：新增支出

输入：

```text
类型：支出
金额：35.5
分类：餐饮
日期：2026-09-28
备注：晚饭
```

结果：

* 成功保存
* 列表出现该记录
* 支出增加 35.50
* 余额相应减少

### Case 2：新增收入

输入：

```text
类型：收入
金额：5000
分类：工资
```

结果：

* 收入增加 5000
* 余额增加 5000

### Case 3：非法金额

输入：

```text
金额：-100
```

结果：

* 保存失败
* 显示错误
* 原输入内容保留

### Case 4：编辑

修改已有账单金额。

结果：

* 原记录被更新
* 不产生重复记录
* 统计同步更新

### Case 5：删除

删除已有账单。

结果：

* 用户确认后删除
* 列表移除
* 统计同步更新

### Case 6：筛选

选择：

```text
本月 + 支出 + 餐饮
```

结果：

* 列表只显示符合条件的数据
* 总支出等统计同步使用筛选后的数据

### Case 7：刷新

新增账单后刷新页面/重新进入页面。

结果：

* 账单仍然存在
* 数据没有丢失

## 8. Phase 7：实现统计


