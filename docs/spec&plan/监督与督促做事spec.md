# 监督与督促做事 spec

版本：2026-09-28 · 模块编号：SUP · 范围：网页端与服务端。

本文区分现状与目标；“必须”描述待验收规范，不代表代码已全部做到。与 [实施计划](<监督与督促做事plan.md>) 配套，跨模块规则见 [总索引](README.md)。来源为 [V1 基线](../09-v1-overview.md)、[第二阶段方案](../10-phase2-product-plan.md)、[首轮实施记录](../11-phase2-implementation.md) 与本次代码核对。新设计细节是本次整理的实现目标；未来扩展不能被自动执行器当作已获授权。

## 1. 目标与模块责任

让用户按约定推进事情：每天有独立执行记录，投入和交付有依据，到点可检查、调整并最终由用户确认。

## 2. 当前实现与缺口

### 已有基础

已有 workRun 每日实例、主动计时、补记原因、文字/本任务成果证据、AI 验收、人工确认、跳过、稍后检查，以及开始/到期/跟进提醒和安静时段。`src/TodayTasks.tsx` 在主页显示今日任务；服务重启暂停活动计时。任务页可看历史。

### 需要补齐

当前日期固定 Asia/Shanghai；历史补做/改期、提交记录或文件证据、结构化多条件验收和每日复盘未完整落地。一次性任务、失败执行器与每日实例的关系需明确；心跳累计计时可能在 AI 验收期间改变 revision，产生无关的并发冲突。错过提醒的合并、通知已读和每日幂等不能只靠 UI 或内存。

## 3. 范围与非目标

本轮做网页内督促；不统计用户在其他软件的使用时长，不推断认真程度，不要求浏览器一直打开才能创建提醒（服务器需运行）。无系统通知、手机推送或后台唤醒承诺。与普通每日待办、要事确认分开。

## 4. 用户流程

确认任务目标及完成条件 → 设置一次性/每日、开始与截止时间 → 生成当日实例 → 提醒并主动计时 → 提交本次证据 → AI 对照条件 → 缺失则补充/改期/跳过 → 全部满足后用户确认 → 历史回看与复盘。

### Q07 已确认：待办升级为监督任务

workRun 的用户含义是“某一天的一次任务记录”；例如每天读书，今天和明天各有一份。监督条件是用户事先约定的完成要求，例如“读30分钟，并写3条心得”。不把技术名字直接放进用户操作文案。

普通待办可由用户显式升级，先确认条件，再建立监督模板/当日实例及 sourceTodoId；操作幂等。同一事项的原待办保留来源和历史，主页/小九提供一个主要处理入口，避免双重催促。只勾普通待办不能跳过监督条件；完成以监督实例的证据、计时和用户确认为准。是否解链或降级不自动新增本次需求。

## 5. 数据与状态契约

workTask 是模板，workRun 是某个日期/计划版本的执行实例；(taskId, localDay, scheduleVersion) 有去重规则，同日改提醒时间不重复生成实例。实例保存条件快照、时区、计划起止、timerSessions、manualAdjustments、evidenceRefs、assessment、confirmedAt、skipReason。
计时、提醒送达和证据版本分别管理，不能把所有心跳都当证据被修改。提醒持久记录 kind、scheduledAt、deliveredAt、snoozedUntil、acknowledgedAt、dedupeKey。升级时不覆盖已完成历史。

本节新增字段是目标契约，不是已落地 schema。实现时优先兼容既有实体，迁移前备份，禁止为了符合新字段丢弃历史数据。

## 6. 功能与异常要求

| 编号 | 要求 | 具体行为 |
| --- | --- | --- |
| SUP-01 | 每日独立 | 每日模板生成独立实例，跨天不清空旧状态；一次性只生成一个实例。旧未完成项由用户选择补做、改期或跳过，不自动完成或重复复制。 |
| SUP-02 | 主动计时 | 明确开始、暂停和结束；补记必须填时间和原因。页面停留不算投入；重启不累计关机时间。展示投入与目标，不用计时宣称已经掌握。 |
| SUP-03 | 完成条件 | 开始前确定必选结果、最小时长、报告/记录要求，默认 AND。条件以本次实例快照为准；修改未来模板不追溯改变历史验收门槛。 |
| SUP-04 | 证据检查 | 支持文字、已有记录、本任务成果和已导入文件引用；校验存在、版本、归属与内容。AI 逐条件给满足/缺少/无法判断、理由和证据位置；标题相似或报告由 AI 生成都不自动满足学习条件。 |
| SUP-05 | 人工完成 | 所有必选条件满足后用户确认 completed；AI 不直接完成实例。重复提交/确认幂等；完成后证据更改需明确重新验收，不能静默改变历史。 |
| SUP-06 | 提醒与调整 | 开始、截止和未完成跟进可见；默认一天最多两次主动跟进（不含开始/截止），尊重安静时段。稍后检查选年月日时分，改期不在旧时间重复提醒，跳过需原因。 |
| SUP-07 | 离线补检查与复盘 | 服务启动后补建必要实例和汇总错过事项，不连发过期通知。每日回顾展示计划、投入、交付、未完成原因和下一步，可按需生成 AI 复盘；不重复索要已提交背景。 |
| SUP-08 | 待办升级 | 普通待办显式升级，确认要求后建立幂等关联；界面用“本次任务记录/完成要求”解释，保留历史，不重复提醒、不绕过验收。 |

## 7. 验收标准

| 编号 | 场景 | 可检查结果 |
| --- | --- | --- |
| SUP-A01 | 双条件门槛 | “45 分钟 + 三要点总结”：仅计时不能完成，仅报告不能完成；两者满足并人工确认后才完成。 |
| SUP-A02 | 跨天/改期 | 跨日生成一次新实例，昨天仍可查；改到某日某时后只按新约定检查。 |
| SUP-A03 | 提醒约束 | 重复轮询、服务重启、安静时段及错过截止均不重复轰炸；历史多个欠项汇总显示。 |
| SUP-A04 | 计时可靠 | 重复 start/stop、补记、关闭浏览器、服务重启均不双计；补记留痕。 |
| SUP-A05 | 证据并发 | AI 检查期间正常计时不会使验收无故失败；真正修改证据则旧结论不能提交。别的任务产物和过期重复证据不得冒充本次新成果。 |
| SUP-A06 | 复盘可核对 | 指定日期回顾数字来自实际执行记录，未完成原因和 AI 建议区分，不能改写历史为已完成。 |
| SUP-A07 | 升级一致性 | 双击或重试只产生一个关联；原待办可追溯，主页和小九不重复催；勾待办不能把未达条件的监督实例标完成。 |

“已有测试通过”仅代表其覆盖的路径；模型请求能返回、页面能打开或接口 health 正常，不足以证明整个模块达标。

## 8. 依赖与后续边界

依赖 ACT 的计划版本与任务状态、REC 的证据引用；先稳定条件快照和日期，再做提醒与复盘。EVT 复核独立，不把待办或要事确认当作 workRun 完成。

P2：系统级使用时长、推送渠道、跨设备离线计时和强制锁机均不开发；生活督促不能演变成未经要求的监控。

## 补充：小九统一提醒（用户最新确认）

本模块产生的业务提醒、监督和需用户处理的提示，必须接入 [小九统一提示表](小九桌宠spec.md)，由小九说出。原模块继续维护权威事实、约定时间、详情及确认操作；不另起一套独立催促。普通就近表单校验/保存反馈不受影响。源事项处理、改期、取消或稍后后同步更新提示，查看/收起小九不等于确认事项。此规则是本轮目标，覆盖旧的提醒表达边界，不表示当前已完成接入。

## 过滤与校验补充（2026-09-29）

遵守 [校验审查中的共同契约](../14-filter-validation-review.md)：候选、已选与可提交使用一致规则；无效已选项必须可见可移除；模型建议不等于有效业务数据。以下是目标约束，不代表代码已修复。

- **V01：** 模型返回值先校验对象结构、类型、长度、枚举及引用。标题/摘要/分类等业务内容超限不能无提示截断；无效必填字段显示具体原因。模型不能写 priority、confirmed、active、revision 等人工/服务端字段。关联建议可过滤去重，但必须返回被移除项的原因；用户已确认输入不能静默过滤。
- **V02：** 候选列表、已选列表和提交校验共用类型/空间/状态/自身排除规则；候选缺页不代表对象失效。已有选项即使不在当前页，也须显示摘要或失效占位及移除入口。提交时重新核验，失败保留草稿，按字段及具体 ID 返回原因。
- **V09：** 程序保存本次必选条件快照，模型逐 conditionId 返回判定和证据；缺项/重复/陌生 ID/未识别状态均不能满足。确认绑定条件与证据版本，时长独立计算；旧成果只能按已约定用途作背景，不能冒充本次新交付。
- **V10：** 逻辑执行日身份与日程版本分离；同一计划日实例原地改约定并递增版本，明确改期的来源与目标，不单凭 scheduleVersion 新建。调度发送前回查实例、约定版本及状态；旧 job 失效。日期/补记时长校验有限值、范围和重复区间。
