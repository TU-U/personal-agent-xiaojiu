## 2. Redis 和消息队列怎么选

消息队列可以理解为后台工作的待处理清单：网页提交工作后，执行进程领取工作，并记录成功或失败。单用户也可能同时上传文件、转写录音和生成报告，因此不必等到大型分布式系统才使用队列。

Redis 是数据服务；BullMQ 是可使用 Redis 实现任务队列的 Node.js 库；RabbitMQ 是消息代理。Redis + BullMQ 是一套组合，不是需要并列安装的两套消息代理。[BullMQ 官方说明](https://docs.bullmq.io/)

| 方案 | 对拾光的意义 | 代价与建议 |
| --- | --- | --- |
| 继续 SQLite 待处理表 + 自建执行器 | 本地部署最少新增服务，能支持低并发工作 | 重试、租约、恢复、调度要自己维护；是有效基线，不因使用 SQLite 就不专业 |
| **Redis + BullMQ** | 适合 Node 后端处理转写、文档解析、Embedding、调研步骤等后台工作 | 新增 Redis 运维与任务一致性处理；已确认采用的队列方案 |
| RabbitMQ | 发布确认、消费确认，以及独立消息代理的投递机制 | 应用仍要实现任务状态、预算和步骤恢复；目前缺少必须使用独立消息路由体系的需求，暂不引入 |

RabbitMQ 的“发布成功确认”和“消费成功确认”是两个不同环节，不能把消息代理收到消息理解成业务已经完成。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

Redis 普通 Pub/Sub 不适合承载不能丢失的待办工作：订阅方断开时可能错过消息。BullMQ 的持久性也依赖 Redis 的持久化配置，并非安装后自动保证不丢数据。[Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)；[BullMQ 部署要求](https://docs.bullmq.io/guide/going-to-production)

本阶段不增加第二套 MQ。若未来出现独立多语言服务、复杂消息分发等明确需求，再重新评估消息代理选型。

## 3. 已确认的职责划分

1. **SQLite：权威业务数据。** 保存记录、要事、记忆状态、任务步骤、用户确认、累计预算和待投递工作。
2. **Redis + BullMQ：安排后台执行。** 保存排队和运行所需信息；消息只携带业务 ID、步骤 ID、预期版本等，不复制整份文件或所有聊天。
3. **执行进程：实际做事。** 领取任务后重新读取 SQLite，核验权限、版本、取消状态和预算，再调用模型或工具。CPU/GPU 密集的本地转写放到独立进程/服务，避免堵住网页 API。
4. **Qdrant：可重建的检索索引。** 保留已确认的向量及关键词混合检索路线，不因截图提到 Chroma 就迁移数据库。
5. **小九：统一展示提醒。** 提醒事实仍归原模块管理；任务进度不等于提醒已确认，更不等于用户已完成事情。

业务变更和待投递项需要在同一 SQLite 事务中提交，再由投递器发送到队列。Redis 不可用时保留待投递状态并显示原因，恢复后补投。这个规则需要实现并验证，不能仅凭现有 `search_outbox` 的名字宣称已有完整事务保障。

工作可能被重复领取。幂等键应绑定业务、步骤和输入版本，并由数据库约束及条件更新保证最终写入不重复。BullMQ 的 jobId 去重不能替代业务幂等；Redis 丢失或清理任务后，还需要根据数据库任务状态对账恢复。[BullMQ 幂等任务](https://docs.bullmq.io/patterns/idempotent-jobs)

外部模型调用超时可能发生“服务商已处理但本地没拿到结果”，不能承诺恰好执行一次或绝不重复计费。应保存调用尝试、使用服务商可用的幂等能力，并将不确定费用纳入预算处理。

## 4. LangGraph 用在哪里

已确认先在“快速学习与调研”接入并验证 LangGraph JS。它负责工作流状态和分支；队列负责何时、由哪个执行进程运行步骤，两者职责不同。LangGraph 的持久化检查点能够记录图执行状态，但副作用、重放和业务幂等仍须正确设计。[LangGraph 持久化](https://docs.langchain.com/oss/javascript/langgraph/persistence)

试点流程：生成计划 → 等待用户确认 → 读取相关本地资料/搜索网页 → 检查证据缺口 → 预算内补充检索 → 整理答案与来源 → 保存成果草稿。

- 联网失败按已确认要求退回模型已有知识，标记“未联网核验”；不伪造来源。
- 等用户确认时保存检查点并释放执行资源；确认后发起恢复工作，不持续占住 worker 或空转调用模型。
- 5分钟、1元按本次调研累计；重试、降级、恢复不能重置额度，价格与计费不明时不能声称硬预算已保证。
- 调研运行 ID、搭子话题 ID 和来源绑定会话 ID 分开，防止一个项目下所有聊天被合并。
- 先验证检查点存储与现有 SQLite 部署的兼容性，不直接假设某个适配器可用，也不为框架另建一份用户长期记忆。
- “帮忙做事”的业务循环继续待讨论。本试点不扩展其工具权限或任务范围。

## 5. 校验、日志和测试同样属于技术补强

已确认新增 Zod 统一检查 API 输入和模型结构化输出；它支持运行时数据校验。[Zod 官方说明](https://zod.dev/)

结构正确后仍必须检查业务合法性：相关要事 ID 是否存在、是否为自身、是否已删除、是否属于可用范围。AI 不能直接决定高低等级、激活记忆、确认提醒或修改用户授权。前端必须能看见并移除失效选项。

日志沿用后端终端和文件日志，增加 requestId、runId、stepId、模型、耗时、费用、重试原因、结果状态。保留 AI 交互的可追踪输出，认证密钥不进入日志。先做到单次任务能查清卡在哪一步，再考虑额外监控平台。

沿用现有测试工具，仅补与变更相关的高价值测试：

| 故障或边界 | 最低验收 |
| --- | --- |
| Redis 停止后上传/提交工作 | 原始资料与待处理工作保存；前端不假报成功完成；恢复后可继续 |
| 执行进程在写结果前后被终止 | 对账后能恢复，结果、提醒、记忆不重复新增 |
| 要事延期或取消后旧工作才到达 | 核验版本与状态后停止旧工作，不发旧提醒 |
| 等待用户确认后服务重启 | 确认状态保留，不能自行越过人工确认 |
| 模型返回自身关联、未知 ID、错误字段或空内容 | 可解释报错/剔除无效建议，不阻碍用户修正；不能绕过正常保存校验 |
| 调研重试和恢复 | 累计预算不重置，达到限制后有明确结果状态 |
| 文件或记忆更新时旧索引工作完成 | 旧版本不能成为有效检索依据；范围过滤继续有效 |
| 慢速转写与普通聊天同时进行 | 独立资源限制生效，API 不被重型计算阻塞 |

## 6. 落地顺序与范围

1. **先定义共用任务契约**：运行/步骤/尝试/版本/状态/预算/确认，明确唯一键与数据库事务；补最关键的现有校验风险。
2. **接入一条队列链路**：优先选文件解析或录音转写，完整展示排队、进度、失败、重试、取消；包含 Redis 持久化、内存策略、启动与恢复说明。
3. **验证调研图执行**：用 LangGraph JS 验证计划确认、联网降级、检查点恢复、预算边界；复用队列，不并行维护两套业务状态真相。
4. **逐步接入索引和到期检查**：保留现有 outbox 的有效机制，采用可回退迁移；定时任务按本地电脑运行条件补查，电脑关机期间无法承诺准点执行。
5. **留下可复现证据**：记录处理时长、失败恢复、重复写入检查和检索样例结果；具体数字在测量后填写，不预先编造吞吐量或准确率。

Redis/BullMQ 管调度，LangGraph 管研究流程检查点，SQLite 管业务事实和确认；它们通过稳定运行/步骤 ID 关联，不能各自维护互相矛盾的完成状态。Redis 故障时业务工作保留在 SQLite 并可补投；该恢复机制不能替代真实队列验收。

LangGraph 检查点适配和 Zod 版本必须在开发时核验；兼容性问题不能静默变成另一套框架已获确认。不能以接框架为由扩展 ACT 未定场景或全量重写后端。ASR/说话人分离的具体模型仍需硬件和质量验证，本次没有确认新的 ASR 型号。
