## 1. 项目体量的真实认知

这不是"具备基础功能的 Demo"。按模块与文档规模衡量，这是一个**生产级水准的单用户本地个人运营系统**：

| 维度 | 数量 | 说明 |
|---|---|---|
| 前端组件 | 63 个 .tsx | React 19 + Vite，响应式覆盖电脑与手机浏览器 |
| 服务端模块 | 90 个 .mjs（4863 行） | Express 5 模块化单体，index.mjs 统一组装；**平均 54 行/模块**——小而单一，问题不在数量而在平铺无层次（见第 9.6 节重组方案） |
| 文档 | 56 篇 | 产品、架构、验收、需求澄清全链路 |
| Android 工程 | 独立工程 | Kotlin 原生，复用同一套 API；2026-09-30 已分离为同级 `../personalagent-android`（见第 9.1 节） |
| 测试 | 四类 | node:test 接口测试、Playwright 双尺寸 e2e、axe 无障碍、检索基准脚本 |

结论：项目复杂度已到达"单人维护的上限区间"，后续每一个新模块的加入都应对照本文的功能边界评估。

## 2. 整体架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 客户端层                                                     │
│   浏览器（React 19 + Vite · 响应式）  │  Android 原生 App    │
└──────────────────────┬──────────────────────────────────────┘
                       │ HTTPS :4317 · Cookie/设备令牌 · 来源校验
┌──────────────────────▼──────────────────────────────────────┐
│ 服务端 · Express 5 模块化单体（78 模块）                       │
│  记录·待办·要事 │ 资料库·解析 │ 搭子会话 │ 记忆系统            │
│  混合检索      │ 小九·监督提醒 │ 成果导出 │ 记账                │
│  ── 基础设施：备份恢复 · 设备认证 · 能力探测 · AI 日志 ──       │
│  ── 一致性基座：revision · opId · changes 游标 · 迟到核对 ──   │
└──────────────────────┬──────────────────────────────────────┘
                       │ SQL 事务 · 增量游标
┌──────────────────────▼──────────────────────────────────────┐
│ 数据层（全部本地 .data/）                                      │
│  SQLite（权威）│ 文件原件 │ Qdrant（dense+sparse）│ Redis·BullMQ│
└──────────────────────┬──────────────────────────────────────┘
                       │ 队列消费
┌──────────────────────▼──────────────────────────────────────┐
│ 独立 Worker 进程（fork · 超时与取消保护）                      │
│  文件解析（PDF/DOCX/编码）│ ASR 转写 │ 向量索引器               │
└──────────────────────┬──────────────────────────────────────┘
                       │ 模型调用
┌──────────────────────▼──────────────────────────────────────┐
│ 模型与外部服务（接口兼容 · 可替换 · 不绑定供应商）              │
│  DeepSeek 兼容（chat/vision）│ Qwen3-Embedding │ Whisper │ Brave│
└─────────────────────────────────────────────────────────────┘
```

三个关键设计决策（理解本项目的钥匙）：

1. **SQLite 是唯一权威数据源，Qdrant / Redis 都是可重建的衍生物。** 检索服务挂了、队列丢了，数据不丢；备份只需 SQLite + 文件原件。这是整个系统能放心折腾的前提。
2. **模型层全部接口兼容、可替换。** DeepSeek 只是"当前默认"，chat / vision / embedding / ASR 全部走适配层。
3. **一致性基座贯穿所有模块。** 每个业务对象带 revision，每次提交带 opId 幂等保护，跨端同步靠 changes 增量游标；"迟到结果不覆盖新数据"是全系统语义。

## 3. 核心功能流程（六步闭环）

从一条记录进门到被小九提醒处理，完整旅程：

```text
 ① 捕获 ──→ ② 解析 ──→ ③ 组织 ──→ ④ 检索与生成 ──→ ⑤ 确认与行动 ──→ ⑥ 小九闭环
    ↑                                                        │
    └────────── 复盘与阶段总结沉淀为新的记录与记忆 ←────────────┘
```

| 步骤 | 要点 | 恢复语义 |
|---|---|---|
| ① 捕获 | 随手记录、录音、文件导入、E 盘导入、账单 OCR；先存原件和 SQLite 版本再谈解析 | opId：响应丢失重试不重复；浏览器草稿可恢复 |
| ② 解析 | Redis/BullMQ 队列 + fork 独立 Worker；文字提取、编码检测、ASR 转写 | 两分钟上限；失败保留原件可重试；迟到结果核对版本，不覆盖用户编辑 |
| ③ 组织 | AI 自动分类 + 标签 + 摘要；片段进 Qdrant（dense+sparse）；对话提出候选记忆 | 人工分类不被迟到 AI 覆盖；单文件可重试索引 |
| ④ 检索与生成 | 关键词 + 向量并行召回，RRF 融合；服务端强制范围过滤；候选回查 SQLite 当前版本 | 引用不实退回原文整理；失败不保存残缺成果 |
| ⑤ 确认与行动 | 候选记忆确认/暂停/删除；要事检查与复核；待办按天管理；待办可升级为监督任务 | 来源变化重新确认，来源删除后失效 |
| ⑥ 小九闭环 | pet-reminders 聚合四类待处理；引导处理 → 证据计时 → 阶段回顾 | 免打扰、按来源去重、只显示最新一条 |

**每一步都有恢复语义**是本项目区别于普通个人项目的地方：大多数个人项目死于"边写边丢数据"，本项目在这一点上已是生产级水准。

## 6. 小九：功能定位与实现考量

### 6.1 三层结构

小九不是桌宠皮肤，**她是监督系统的拟人化前端**——4.5 分复杂度的引擎是本体，2 分复杂度的形象只是"脸"。这个分层是对的。

```text
┌────────────────────────────────────────────────┐
│ 表现层 · PetBuddy.tsx（纯前端 · 2/5）            │
│   10 种心情 · 事件驱动状态机 · 拖拽/Q弹/打盹     │
├────────────────────────────────────────────────┤
│ 交互层 · 与用户的接触面                          │
│   陪伴聊天（/api/pet/chat·带记忆上下文）         │
│   提醒面板（角标+清单·同源版本快照）              │
│   引导直达（actionTarget 页面跳转）              │
├────────────────────────────────────────────────┤
│ 服务层 · 真正重的引擎（约 10 模块 · 4.5/5）      │
│   提醒聚合 pet-reminders：要事检查·今日待办·      │
│     记忆确认·监督逾期·免打扰·去重                 │
│   任务监督 supervision：workTask 模板 → workRun  │
│     每日执行·条件快照·计时·证据·复盘 recap        │
└────────────────────────────────────────────────┘
```

### 6.2 定位判断

1. **她是系统唯一的"主动交互界面"。** 普通功能都是用户发起、系统应答；只有小九会主动找用户。未来所有"系统主动找用户"的功能都应经小九的口说出，保持人格一致，不另设通知中心与她抢戏。
2. **人设与机制分离。** 下一步把小九的语气、口头禅、表情素材做成可配置的"人设包"，与监督引擎彻底解耦——换形象换性格，引擎不动。
3. **真实原型是独有优势。** 朋友的宠物、真实照片——有故事、可信、非虚拟 IP。可让她有"自己的日常"（真实宠物新照片、小动态），形成任何产品抄不走的情感锚点。
   - 素材授权已与朋友确认：照片随开源仓库公开（2026-10-07，见 9.5 节）；**商用须另行取得明确授权**。
4. **主动性走"数据驱动"路线（已确认）。** 只在 recap / 复盘有关键数据时主动搭话（如每周一次阶段总结：有依据才开口，如"这周你完成了 4 次跑步，比上周多一次"），不做为说话而说话的定时问候。频率、免打扰、可关闭三条底线先立好。
5. **她应是"阶段总结与行动建议"的讲述者。** 项目最初需求"根据已有内容生成阶段总结与后续行动建议"，原料恰好是监督 recap（证据、完成率）+ 检索 + 记忆。让小九来说这些总结，功能与角色合一——这是本项目最自然的差异化。

## 7. 定位、边界与方向（已确认）

**定位：单用户、本地优先的"个人运营系统"**，三层价值：

| 层 | 内容 | 对应模块 |
|---|---|---|
| 记忆层 | 第二大脑：资料 + 长期记忆 + 混合检索 | 资料库、记忆系统、检索、会话 |
| 行动层 | 外置的执行监督：待办 + 要事 + 证据闭环 | 待办、要事、监督系统 |
| 陪伴层 | 黏性引擎：小九 | PetBuddy、pet-chat、pet-reminders |

个人工具最大的死因不是功能不够，而是弃用——陪伴层正是解药。

### 7.1 功能边界（守住）

- **保持单用户、SQLite + 本地文件的单服务器架构**——对一个人绰绰有余，且是隐私上的根本优势；
- **Android 端定位薄客户端**（录入 / 查看 / 提醒），**M2 完整离线目标正式搁置**（会引入冲突合并，复杂度直接上一个量级）；
- **记账、截图 OCR 等外围模块降级为维护模式**（实际使用约一月三次），精力留给核心链路；
- 不做多人 SaaS，不参与通用笔记软件的功能竞赛（协作、富文本等）。

### 7.2 发展路线

| 阶段 | 内容 |
|---|---|
| **巩固期（现在）** | ① 把一致性基座写成文档 + 回归测试守护（最急迫：最值钱的资产没有守护）；② **`server/` 模块按职责域分层**（见 9.6，index.mjs 拆分的前置）；③ index.mjs 按路由拆分（已接近 150 行 import、数千行组装）；④ 接入层重构——pi-agent 统一接管模型适配（进行中，见 9.2）；⑤ 多端协议 Schema 独立模块 + Submodule + `/v1/` 语义化前缀（见 9.3） |
| **深化期（下一步）** | 小九：数据驱动主动性（recap 素材的每周阶段总结对话）+ 人设配置化 + 阶段总结讲述者；Electron 桌面壳常驻桌面（见 9.4） |
| **长期** | 以小九为差异化做纵深质量：真实宠物原型的陪伴 + 可审计的监督闭环——项目独有、别人抄不走 |

## 9. 架构演进增补（2026-10）

2026-09-30 至 10-08 期间讨论并落地的演进决策。**已执行的写成事实，未执行的标注状态。**

### 9.1 Android 工程物理分离（已执行 · 2026-09-30）

`mobile/` 整体迁出为同级的 `../personalagent-android` 独立工程（约 12 GB，含 node_modules 与构建产物），随迁 Android 设计文档（`docs/mobile/`）、APK 与验证产物（`artifacts/mobile/`）、adb 工具（`.android-tools/`）和两个手机开发启动脚本（相对路径已修正）。

**留在本项目的**：后端 `/api/mobile/v1/*` 路由（`server/core/studioice-auth.mjs`）及对应测试（`tests/mobile.test.mjs`、e2e bridge 测试）——它们是服务端能力，App 只是消费方。

**体量认知修正**：主项目从约 20 GB 降至 8 GB。78 个服务端模块**不是臃肿的来源**——模块化单体的小而单一模块是健康形态；真正的体积大头是运行时与数据，而非代码：

| 目录 | 体积 | 性质 |
|---|---|---|
| `.data/` | 2.9 GB | 全部个人数据（SQLite、原件、备份），绝不能进 Git |
| `.local-runtime/` | 2.5 GB | 本地运行器（Redis、Whisper 等可执行程序），可重装 |
| `.local-model/` | 2.2 GB | 本地模型权重，可脚本重下 |
| 代码本体（src+server+tests+docs） | 约 15 MB | — |

### 9.2 Pi 模型接入与 Agent 循环（方案 B 已确认 · 待实施）

2026-10-08 用户选择方案 B：统一模型调用，同时接入 Agent 循环，先在搭子中支持按问题检索记录、读取要事、调用搜索，再综合回答。这里确认的是接入方向，尚未安装依赖或替换运行时。

- 项目为 [Pi](https://github.com/earendil-works/pi)（原 `badlogic/pi-mono`）。`pi-ai` 负责统一模型调用；`pi-agent-core` 负责模型与工具之间的执行循环。具体依赖版本实施时锁定。
- 搭子的工具复用拾光业务服务；现有调研 LangGraph 流程、长期记忆人工确认、SQLite 权威状态和业务校验继续由拾光管理。
- 修正原文“chat / vision / embedding / ASR 全部由 Pi 直接接管”的表述：已查阅的Pi接口文档支持模型生成、图像输入及工具调用，未确认统一embedding/ASR接口；现有Qwen embedding、本地ASR保留专用适配，通过拾光统一能力入口组织。
- **接入与升级方式已确认（2026-10-08）**：Pi直接集成在拾光后端，随拾光安装和升级；页面负责管理模型及能力配置，暂不开发插件上传、安装、升级或卸载系统。原文“通过管理后台导入”由此条替代；这不包含开放任意文件操作或接入完整编程助手。
- 费用事实：Pi源码采用 [MIT许可证](https://github.com/earendil-works/pi/blob/main/LICENSE)，本地嵌入SDK无需购买Pi订阅；外部模型及付费搜索服务按供应商计费。多轮工具循环可能增加模型调用与上下文用量。
- **搭子循环上限已确认（2026-10-08）**：一次回答最多6次模型调用、2分钟、1元预算，达到任一上限即停止追加调用并展示已有结果，由用户选择是否继续；重试计入同一预算。正式调研仍沿用原先5分钟/1元及计划确认规则。

### 9.3 多端协议治理：独立 Schema + Submodule + 语义化版本（首批已实施，尚未全部完成）

**方案确认（2026-10-08）**：用户已确认以下六项方案，独立协议仓库命名为 `xiaojiu-contracts`。当前状态为“首批已实施，尚未全部完成”：152个接口已逐项映射并保留旧入口，57个操作已抽取本轮形状，92个复杂操作待继续抽取，3个保持已退役。协议远端已发布，Android接入尚未完成，见[实施记录](26-contract-governance-implementation.md)和[迁移清单](25-contract-migration-inventory.md)。

#### 当前代码事实

- 主项目已有 `.gitmodules` 与真实 `contracts/` Submodule，锁定本地独立 `xiaojiu-contracts.git` 仓库的 `v0.1.0`；协议与v0.1.0标签已发布至GitHub `TU-U/xiaojiu-contracts`。
- Web请求、图片与下载入口已切到 `/api/v1`；后端依照协议逐项登记别名，保留旧 `/api/...` 和 `/api/mobile/v1/...`。设备新入口为 `/api/v1/devices/*`，不会与Web会话混用。
- `contracts/openapi.json` 已生成公共TS类型，`src/types.ts` 消费生成物，后端Ajv校验首批JSON请求；原Zod和业务校验保留。复杂业务局部类型与Android尚未完成共享协议接入。
- Android已独立仓库；桌面壳将复用Web前端和同一后端，不需要第三套手写模型。尚未改动Android工程或运行手机测试。

#### 已确认的实施方案

| 项目 | 已确认方案 |
| --- | --- |
| 协议源格式 | 用OpenAPI 3.1系列描述HTTP接口，使用其JSON Schema能力定义请求、响应和公共数据结构，作为跨语言协议的唯一来源；首批已锁定OpenAPI 3.1.1、openapi-typescript 7.13.0及Ajv 8.20.0。 |
| 独立仓库 | 仓库名称已按用户要求确定为 `xiaojiu-contracts`，各消费仓库以 `contracts/` Submodule引用明确提交。协议使用版本标签发布，更新Submodule指针是显式升级，不自动跟随最新分支。本地仓库与Submodule已创建，协议提交与v0.1.0标签已发布。 |
| 共享范围 | 共享路径、方法、请求/响应字段、公共实体视图、错误、分页/游标、revision与opId语义、上传下载及流式事件约定；数据库SQL、业务状态机、权限判断、模型提示词留在后端。 |
| 版本口径 | 协议包采用 `1.0.0` 等SemVer；新统一路由以 `/api/v1/...` 为主版本前缀，未来不兼容演进使用 `/api/v2/...`。OpenAPI格式版本、协议包版本、API主版本三者分开。 |
| 迁移方式 | 新路由与旧 `/api/...`、`/api/mobile/v1/...` 过渡并存，复用同一业务服务和数据；按接口清单映射，不用整站路径替换或重定向写请求。旧接口移除需另有明确退役计划和客户端升级证据。 |
| 实施顺序 | 协议盘点与抽取 → 独立仓库/Submodule → 服务端v1兼容入口与校验 → Web消费 → 未来桌面壳复用 → Android单独阶段接入。当前阶段不打包或测试手机；Android未接入前不能宣称多端治理全部完成。 |

选用OpenAPI的依据是其跨语言HTTP描述能力及JSON Schema支持，见 [OpenAPI官方规范](https://spec.openapis.org/oas/v3.1.1.html)。Submodule记录特定提交，不会让所有客户端自动同步升级，见 [Git官方文档](https://git-scm.com/book/en/v2/Git-Tools-Submodules)。协议版本规则依据 [SemVer](https://semver.org/)。以上路线已获用户确认，首批本地接入已实施，完整进度以本节实施记录为准。

#### 必须保留的业务与兼容边界

- 共享Schema检查的是数据形状；“关联要事是否存在”“是否引用自身”“revision是否过期”“记忆是否经用户确认”仍由后端按当前业务状态校验。不能把Zod业务校验机械搬出后删掉。
- 主协议确定后，从其生成或派生TS类型与可执行形状校验；Android阶段再核验Kotlin生成或消费方式。代码生成器的实际兼容性需验证，不能只复制两份定义后称为共享。
- 迁移时保留既有Cookie/设备令牌身份边界、错误状态与响应字段（包括error/current），需要的新字段增量加入；流式回答、下载和上传不能套普通JSON响应后破坏现有调用。
- 请求与响应的兼容性分别检查。增加必填输入、收紧约束、删除/改名字段、改变字段类型或认证行为属于潜在破坏性变化；新增响应枚举值也须检查旧客户端解码能力，不能一律当成兼容小版本。
- 旧、新路径复用原事务、操作回执与幂等身份，不能按路径版本重复创建业务操作。实体revision与协议版本无关，不能因切API版本而重置数据或游标。
- 首轮先用现有可工作协议建立基线，再分模块迁移。协议覆盖清单记录每条接口的请求/响应、旧路径、v1路径、消费者及接入状态，不能仅创建一个Schema仓库就标记完成。

#### 分阶段完成条件

1. **实施准备**：六项方案、接口迁移清单和工具版本已落地（OpenAPI 3.1.1、openapi-typescript 7.13.0、Ajv 8.20.0）。动态字段及复杂接口形状仍需按清单继续抽取。
2. **主项目落地**：独立仓库可供引用，Submodule固定版本，服务端和Web实际消费，代表性读写、鉴权、错误、幂等及上传/流式路径的定向验证通过；旧入口兼容可用。这里只能报告服务端/Web阶段完成。
3. **多端闭环**：Android在其独立仓库升级到明确协议版本，并完成对应接入验收；桌面壳复用同源Web接口。当前不做手机工作，此项明确留待后续，不能用Web通过替代。

2026-10-08首批实施：已接入本地独立仓库/Submodule、生成公共类型和校验、增加v1入口并迁移Web；6项接口测试、1项桌面网页测试及构建通过。已沿用原环境和数据目录重启4317服务。本地协议使用0.1.0，协议远端已发布；完整字段抽取和Android接入未完成，不能将本节标为完成。

### 9.4 小九桌面常驻：Electron 桌面壳（规划）

**桌面壳含义与数据关系已澄清（2026-10-08，用户确认）**：本节的“桌面版”统一理解为「拾光桌面壳＋桌面小九」：复用现有Web主界面，通过Electron承载主窗口、独立小九窗口与托盘。网页与桌面壳连接同一后端，共用SQLite与文件，不维护两套需要互相同步的数据副本。两个界面同时打开时的数据变更通知、自动刷新和编辑冲突处理仍需落实，不能把共用数据库描述为已完成实时界面同步。本轮仅更新方案，尚未开发桌面壳或制作安装包。


现状小九是 Web 前端内的浮层组件（`PetBuddy.tsx`），关掉浏览器即消失。规划以 **Electron 将现有 Web 前端包装为桌面壳**：透明窗口 + 系统托盘，小九常驻桌面。

架构约束不变：**情绪状态机（表现层）与监督引擎（服务层）保持解耦**——桌面壳只是换了"脸"的宿主，引擎仍在本项目后端。这也与 6.2 节"人设与机制分离"的路线一致。

**桌面版启动体验已确认（2026-10-08，待实施）**：

- 双击拾光即可使用：自动启动所需本机后台服务，再显示主界面和小九，日常使用不要求手动运行终端脚本。
- 已有拾光后台运行时复用已有服务，避免启动两套服务；实现时核验服务身份、兼容性与数据目录，不能仅凭端口被占用就认定可复用。
- 网页与桌面版使用同一份业务数据，不另建独立桌面数据库。
- 启动失败时在界面显示原因，提供查看日志与重试入口。
- 服务打包和进程管理的具体实现另行设计；开机自启默认开启（用户已确认），可在设置中关闭；共享后台的退出范围按下文已确认规则处理。

**关闭窗口与重新打开已确认（2026-10-08，待实施）**：

- 点击主窗口「×」仅收起主界面，小九继续留在桌面，后台任务和提醒继续运行。
- 托盘可重新打开主界面，并单独提供「退出拾光」，区分关闭窗口与退出应用。
- 小九新增明确的「打开主界面」按钮；与托盘入口使用同一窗口恢复逻辑。作为实现约定，窗口已存在时恢复并聚焦，连续点击不重复创建窗口或后台服务。
- 保留「交流」「汇报」「提示语」原有职责；点击角色本体仍为摸摸。「打开主界面」只负责导航，不确认或消除待处理提醒。

**开机自启展示已确认（2026-10-08，待实施）**：支持开机自启；通过开机自启进入时只显示小九，不自动弹出主界面。主界面通过小九「打开主界面」按钮或托盘入口打开。沿用已确认的后台启动/复用机制。设置提供开机自启开关，默认开启，用户可关闭（2026-10-08最终确认）；自启只显示小九。本轮仍仅记录产品方案，不在讨论阶段修改当前操作系统的自启设置。

**主动退出时的任务处理已确认（2026-10-08，待实施）**：

- 用户点击托盘「退出拾光」时，有执行中的任务则提供两项选择：「继续后台运行」收起界面并保留任务执行；「确认退出」停止当前执行、保留已保存进度，下次打开明确提示需要恢复或重试的任务。
- 没有执行中的任务时直接退出，不增加无关确认。
- 工程实现需区分可恢复检查点与只能重试的任务，不能承诺所有外部模型请求都能断点续跑；退出不得把未完成任务标为成功。后台进程的停止范围按下文规则处理，不能用直接杀共享进程代替任务收尾。

**桌面壳退出时的共享后台边界已确认（2026-10-08，待实施）**：

- 桌面壳接入原本已运行的后台时，退出桌面壳保留该后台，让网页继续使用。
- 只有桌面壳自己启动且由它独占的后台，才随退出关闭；“自己启动”不自动等于“仍然独占”。
- 正在执行的任务仍按前述退出选择处理；工程实现需区分本次桌面执行与其他入口的执行，不能将桌面退出扩大为停止整个共享后台中的全部任务。
- 实现时记录服务启动归属并核验是否仍独占，不能只凭进程名、端口或初次启动者判断。无法确认独占时保留共享服务；共享使用状态的具体识别机制在实现方案中设计。
